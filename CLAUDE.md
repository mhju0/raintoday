# Claude Code repository guidance

오늘비 is a South Korea local rain forecast: it compares next-day precipitation at a validated user coordinate and can weight providers by recently observed performance at a nearby KMA ASOS station. It grew out of a Seoul-only cinematic weather scene; that scene, the radar stack, and the second scoring pipeline are gone from the tree, and nothing renders behind the forecast. Keep changes focused on maintenance, correctness, security, and compatibility; do not add new product scope unless explicitly requested. `README.md` is the canonical public overview and `CONTEXT.md` is the domain glossary.

## Runtime and commands

- Node 22 or newer; npm with the committed `package-lock.json`.
- `npm run dev` — local server at `http://localhost:3000`.
- `npm run lint` — ESLint.
- `npx tsc --noEmit` — strict TypeScript check.
- `npm test` — Node's native runner over `lib/**/*.test.ts`, then the focused TSX/JSDOM component suite.
- `npm run build` — production build; `next/font` needs network access to fetch Geist and Noto Sans KR during a clean build.
- `npm run service:health` — checks the deployed service (page, forecast, administrative search) and Pirate Weather's remaining quota against the pipeline's projected burn. Runs every six hours from `service-health.yml`; nothing else watches the served path, and production keys live in a different store than the scheduled jobs' secrets.
- Offline and scheduled work, none of it on a request path: `performance:capture` (the cohort run behind `local-performance.yml`), `performance:observations`, `performance:seed`, `performance:catalog`, `service-area:generate`, and `location:matrix`. Every one that needs a credential already loads `.env.local` through `--env-file-if-exists`, so none needs a `KEY=… ` prefix; `service-area:generate` takes no environment at all. Note `scripts/generate-station-catalog.ts` still documents a `KMA_APIHUB_KEY=… ` prefix in its header comment — that is stale, not a second convention.

The application works without environment variables. Copy `.env.example` to `.env.local` only to enable optional server-side providers. That file declares exactly eight variables and code reads every one of them; a variable nothing reads any more belongs out of the file rather than kept "for reference", because a stale example is how a dead key survives a cleanup. Never expose provider keys through `NEXT_PUBLIC_*`, logs, errors, fixtures, or responses.

## Architecture

- `app/page.tsx` renders `LocalForecastExperience` — the location chooser and, once a coordinate is chosen, the forecast dashboard — plus the `<noscript>` notice. It carries no `metadata` export; the root layout owns the title and description.
- The served surface is small and fixed: `/`, `/behind-the-data`, `/api/local-forecast`, `/api/locations/search`, the static `/icon.svg`, and the rendered `/opengraph-image`. `/atmosphere` and `/diagnostics` still redirect to `/` through `next.config.ts` — real HTTP redirects for the retired scene's old paths, independent of JS. No other route is served; unknown paths 404. The API surface stays at two: `/behind-the-data` reads the performance store from its server component rather than adding a third.
- The dashboard is one vertical read with no ambient scene behind it: the rain window as a sentence (carrying the window's own mm total when the data supports one), a pinned sparkline miniature of the ribbon that doubles as navigation and carries the 한눈에 ⇄ 전체 근거 density toggle, the horizontal 24-hour ribbon (eight 3-hour blocks with an mm lane beneath them), the 오늘 / 내일 cards (probability and amount co-equal), then — on the receipts shelf — two evidence cards and the scored per-provider table. Each stratum opens with a claim kicker naming whose number it carries (결론 / 오늘 · 내일 — 여러 서비스를 섞은 / 근거 / 기록, ADR 0010); the kickers are labels, never a numbered sequence (0010 rejected 01–05 chapter numbering). Its interactive controls are "위치 바꾸기", the density toggle (persisted in `localStorage`), the timeline scrub lens (pointer or arrow keys), and — only while folded — the summary stubs that unfold their own sections. Nothing else.
- The chooser, the loading overlay, and the failure card share that vocabulary: one flat ground, mono meta, 3px corners, and colour reserved for the three things that carry meaning. On the dashboard the ground stays flat for the answer, and only the receipts shelf — exactly what the density toggle folds — sits one surface rung up behind a single hairline (ADR 0010 amending this rule); every separator that pass added is achromatic. Colour is still reserved for the three things that carry meaning — the chance of rain (blue), the amount of rain (water-teal, ADR 0009), and the rain window itself (amber). The scoring record at `/behind-the-data` shares the forecast's token block — `.local-forecast-page, .btd-page` — because scoping those custom properties to one page class left the record on browser fallbacks, close enough to correct to survive a screenshot. `.btd-page` is the ground and `.btd` the reading column; the forecast page's own frame declarations are deliberately not shared. It adds no status palette of its own: its verdicts are told apart by their words, because a state that borrowed one of the three meaning-colours would be claiming to be one of them. Nothing on any of these five surfaces may reintroduce a decorative palette; the page is read, not looked at. The chooser and the loading overlay both draw the timeline's empty frame — gridlines and a sentence, no data claims — and the loading frame pulses as one whole, never per provider.
- `/behind-the-data` is the scoring record: what the benchmark has decided, on which station's evidence, and the conditions under which the app stops trusting its own learning. It is a server component reading the same `readDatabaseEvidence` the forecast uses, with `lib/behindTheData.ts` deriving the view. It takes its coordinate from `?lat`/`?lon`/`?name` — the evidence status chip and the footer link both carry the visitor's own — and falls back to Seoul for anything absent or outside the service area rather than erroring. `RecordStationPicker` re-points it through `/api/locations/search`; the API surface stays at two. Every mode the profile can hold has its own sentence there, the seed is never reported as learned weighting, and the benchmark table states the benchmark's verdict rather than what is being served — those three are what the page's honesty rests on, and each is pinned by a test.
- Forecast providers use `WeatherProvider.read()` to return one Provider Snapshot: availability, cache freshness, and normalized current, hourly, and daily weather from the same cached generation. It has exactly two consumers — `lib/localForecast.ts`, which answers `/api/local-forecast`, and `lib/performance/capture.ts`, which freezes a cohort's forecasts for later scoring. Both call it the same way, over the one `forecastProviders` list.
- `lib/cache.ts` provides process-local single-flight TTL caching with stale-on-error fallback. `lib/providerCache.ts` holds the one TTL they share; it is the former `lib/seoul.ts`, kept only because the TTL outlived the fixed Seoul coordinate that file existed for.
- `lib/performance/` is the only precipitation-scoring pipeline. `runPerformanceBatch` reads the ASOS station catalog, stores the observations a cohort may legitimately ask for, captures that cohort's forecasts per station, and reports its own degradations rather than swallowing them; `scripts/local-performance.ts` runs it from `local-performance.yml` at the two scheduled KST cohorts and persists to PostgreSQL. The cohort label names the scheduled slot, not the hour a run actually started — GitHub schedules are best-effort and observed starts drift by hours — so lead time varies inside a cohort. A delayed scheduled run is never refused — a late capture is still evidence — but `manualCohortHourMismatch` refuses a manual dispatch whose cohort the clock contradicts, and `RecentPerformanceProfile.leadTime` measures the spread so it cannot go unnoticed. It is reported, never filtered from scoring: providers inside one capture share its lead time, so the drift is noise on both sides of a comparison rather than bias (#118). `lib/performance/README.md` is its reference.
- `lib/performance/precipSkill.ts` is served. It was `lib/reliability/score.ts`, and `lib/performance/seedScore.ts` calls `scoreSourceDay` on every request for as long as evidence is in seed mode. Moving it is what let the rest of that directory be deleted; it is not scheduled-only code, and a grep at directory granularity is what made it look that way.
- The scheduled `lib/reliability/` pipeline is gone, with its CLI, its workflow, and the `GitStateTarget` that published to the public `reliability-state` branch. ADR 0007 decided to keep it running unread and revisit; the retirement supersedes that decision, so read the record as history rather than as a live commitment. The branch still exists on the remote and nothing writes to it.
- `local-performance.yml` runs its cohort twice when the first attempt fails: a `retry` job on a fresh runner, which is a fresh egress address. The blackouts behind #103 followed the runner's address, not the hour, so neither moving the cron nor a longer in-run backoff could have helped. The first attempt tolerates its own failure and publishes the verdict as a job output, so a run the retry rescues finishes green and only a double failure alerts; the failed step, its warning, and the retry job's presence keep the blackout visible. The hourly `egress-probe.yml` that measured this is deleted, its question settled.

## Invariants

- Keep Seoul time calculations pinned to `Asia/Seoul`; never use the browser timezone for weather or sun-phase decisions.
- Validate every forecast coordinate against the generated service-area geometry before KMA grid conversion or any provider request. Keep that geometry server-only, regenerate it only from the official SGIS package with `scripts/generate-service-area.ts`, and re-verify the island corpus whenever it is regenerated. Never commit the raw boundary package.
- Preserve the Provider Snapshot boundary: status/cache freshness and weather must come from one provider read. Reuse the shared provider cache; omit non-OK or target-date-missing sources from consensus rather than fabricating values. Stale last-good snapshots remain available with their matching weather.
- Absence of evidence is never evidence of poor performance. A provider short of `minimumSamples` is held at its equal share, never at `weightFloor` — the floor is reserved for a provider that has been measured and scored badly. The seed path already carried this rule for a provider with no archive proxy; #122 is what the live path did without it, and KMA is the source it would have demoted, for lagging on captures because it is the one the egress blackouts hit.
- Preserve the seed evidence boundary. Retrospective Seed Comparisons are scored on amount, stored in their own table, and carry no cohort and no frozen blend, so they can never reach the Prospective Benchmark. Seed influence stays capped, never rescues a benchmark suspension, and is superseded entirely once live evidence matures. Never seed a provider that has no honest archive proxy, and never hand-edit `lib/performance/stationCatalog.ts` — regenerate it with `npm run performance:catalog`.
- A capture is refused outright when a compared provider's read faulted. Serving may omit a non-OK source — the reader is shown what exists — but a capture is frozen and `saveCapture` is `on conflict do nothing`, so a capture short one provider by fault is permanent and indistinguishable from an honest one. `error` is a fault and refuses the capture; `needs-config` is an honest absence, because no runner will ever supply a missing key. This is why the 18 KST cohort's KMA-less rows could never be repaired. Refusing is not the same as alerting: because a refused capture stores nothing, a few of them are missing data rather than wrong data, so `cohortRunFailed` fails the run only past `CAPTURE_FAULT_TOLERANCE` of the cohort. Observations keep zero tolerance.
- An observation that could not be read is never scored as an absence. `absent` means ASOS published no row for that station-day; anything else — a dropped connection, a throttle, a refused key, an unparseable body — is a fault that must land in `failures` and fail the run. Collapsing the two is how a green run stored 10 of 97 observations and reported nothing wrong. Throttled and dropped reads retry with a short backoff; a refusal is terminal and must not be retried, because it only spends quota. A day ASOS has not compiled yet answers the same NODATA as a station with no row, so never point a cohort at a day the record cannot have: the 06 KST cohort reads two days back and only the 18 KST cohort reads yesterday.
- Only a station catalog the run actually read may retire or activate a station. When the apihub catalog is unreachable the cohort falls back to the active stations already recorded, skips `syncStations` entirely — including the drop guard, which is meant to halt a run on a suspicious catalog, not to bless a substitute one — and reports `catalogSource: "store"` so a degraded run is never silent. Never feed the fallback list to a sync, and never let a batch report an empty cohort when it has no station list at all.
- Preserve forecast-provider order: Open-Meteo, KMA, Pirate Weather, then WeatherAPI. The first available current snapshot remains the comparison primary. `lib/providers/registry.ts` exports one list, `forecastProviders`, and the two-list split that used to be mandatory here is gone with the reader that required it: only `lib/reliability/` read the wider list, so it could score MET Norway on terms the forecast path rejected. MET Norway is no longer implemented at all — it answers `ok` for Korea and publishes an amount, but no `probability_of_precipitation`, and both scoring gates require a next-day probability. A new source joins that one list; do not restore a second one.
- `PrecipProviderId` and `ProviderId` still name `met-norway` on purpose, even though no provider module implements it. Stored capture and seed rows carry that id historically, and `PERFORMANCE_PROVIDERS` is the filter that drops it at read time. Removing the id would not delete the rows; it would only stop the code from being able to describe them.
- The ribbon's bars are a plain 0–100% scale with the umbrella threshold drawn at the probability it names — never a compressed scale that would put the mark somewhere other than its own value. A block with no published probability is hatched and unfilled; a published 0% keeps a real, thin bar. The rain window comes from `readTimeline`, and an unpublished block ends a run rather than extending it, so the page claims an end time only when a later block proved one.
- The density fold is honest in both directions. A first visit (unset `raintoday.view-density.v1`) opens at 한눈에; a stored choice is never overridden; and a forecast with no timeline — whose minibar carries the only toggle — never folds at all, because a fold with no unfold control is a locked door. What folds leaves summary stubs that repeat the sections' own numbers (the influence card's header spread, the evidence status label) — never a figure computed for the stub — and the receipts shelf wraps exactly what the toggle governs, so the raised surface and the fold can never disagree.
- The mm lane under the bars keeps its own scale and never shares the probability's value axis — the two quantities share only the time axis. Its amounts are the ribbon provider's own hourly sums (`precipSumMm`); a block whose hours publish no amount is a hatched lane cell, never 0, while a published 0 keeps a real tick. The verdict sentence's total ("— 모두 N mm") is the run's own sum and appears only when the run ends within the series and every run block published an amount. Tomorrow's card attributes its amount spread as named-provider min/max — never quartiles or percentile wording at n ≤ 4.
- The ribbon is one provider's hourly series while the 오늘 / 내일 numbers are a multi-provider blend. Keep them attributed apart; never let the ribbon read as consensus. Performance weighting applies to tomorrow only. The pinned minibar is that same ribbon's miniature — identical data, hatched gaps preserved at minimap scale — which is why sharing the ribbon's colour is correct there and nowhere else.
- The same rule binds inside a card: the amount is a mean of only the providers that publish one, which is fewer than the probability beside it, so a card's provider-count tag must never stand for both numbers. `blendPrecipitation` reports `amountProviderCount`, and the amount carries its own count whenever the two differ.
- A provider that is missing, unconfigured, or failing must leave an honest fallback rather than a blank panel or a fabricated value.
- The two failure shapes stay distinct: `retry` is null exactly when the same request can never succeed, and that card must offer no retry. The loading screen may name the providers being contacted but must never claim per-provider progress — `/api/local-forecast` answers once, so any such row would be invented.
- `COMPARED_PROVIDER_NAMES` and `VERIFICATION_STATION_COUNT` are what the chooser asserts before anyone commits a coordinate. The station count is a literal because the generated catalog must not reach the client bundle; a test pins it to `FALLBACK_STATION_CATALOG.length`.
- Preserve required attribution for Kakao Map (administrative search), Open-Meteo, 기상청 — both the short-term forecast and the ASOS observations the scoring rests on — Pirate Weather, and WeatherAPI. Those are the sources whose data the page actually shows. CARTO/OpenStreetMap and RainViewer are deliberately no longer credited: they credited the radar basemap and approach signal, and the radar is gone, so naming them would describe something the reader is not being shown. MET Norway is absent for the same reason. The credit list follows the served data and nothing else.

## Code conventions

- Test-reachable `lib/**` modules use explicit `.ts` extensions for relative imports so Node can run TypeScript tests directly. Next.js app/component imports use the `@/` alias.
- Keep `vercel.json`'s `deploymentEnabled` guard for `reliability-state`. Nothing writes to that branch now, but it still exists on the remote, and dropping the guard would let anything pushed there produce a deployment. Generated pipeline state never belongs on a release branch either way.
