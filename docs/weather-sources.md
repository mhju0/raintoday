# Weather and environment sources

오늘비 accepts validated coordinates inside the supported South Korea service area and uses `Asia/Seoul`. Exact-coordinate validation tests the coordinate against official SGIS 시도 boundary geometry, so sea and cross-border coordinates are rejected; see [`docs/research/sgis-boundary-acquisition.md`](./research/sgis-boundary-acquisition.md) for the source package, terms, boundary vintage, and update procedure. The geometry is generated offline into a server-only asset and is never sent to the browser. On a cache miss, forecast providers receive the submitted coordinate. Process-local provider caches use a truncated SHA-256 digest of the complete validated numeric coordinate: raw coordinates do not appear in cache keys, and distinct coordinates do not intentionally share provider snapshots. This preserves the Forecast Location contract instead of quantizing one user's response onto another user's coordinate. The exact coordinate also determines the request's KMA grid and observation-station match. The local-performance collector separately requests forecasts at official KMA ASOS coordinates. All upstream calls run on the server. Provider keys and database credentials must never be returned to the browser or written to logs.

The application remains usable without weather-provider keys: Open-Meteo is keyless and supplies a complete forecast on its own — current conditions, the hourly series behind the ribbon, and the daily probability and amount. Manual administrative-area search requires a server-side Kakao REST key, which is also what resolves a device coordinate to its 시·구·동 name; browser current-location selection remains available without it, under the generic "현재 위치" label. The other forecast sources widen the comparison and fail independently.

Pirate Weather is the only upstream with a ceiling this project can actually reach: 10,000 calls a month against a scheduled pipeline that spends two per station per day. A fixed "warn under N left" threshold cannot express that, because the same number is comfortable on the last day of a billing period and fatal on the first, so `npm run service:health` compares what is left against the burn still to come plus a reserve held back for visitors (`lib/quotaRunway.ts`).

### How the ASOS daily precipitation columns are read

Ground truth is `sumRn` (일강수량) from `AsosDalyInfoService`, one row per station-day, requested with `startDt = endDt = ` the KST calendar date being scored. Three properties of that column are load-bearing and were verified against 3,650 station-days across ten stations over calendar 2025:

- **`sumRn` accumulates over the 00:00–24:00 KST calendar day**, aligned to the forecast day. This is not an assumption: KMA publishes the 09:00–09:00 total as a *separate* field, `n99Rn`, and the two disagree on more than half of rainy days (July 2025 at 서울 108: eight of fifteen). A 9-9 boundary would have shifted overnight rain into the neighbouring day and charged systematic misses and false alarms; it does not.
- **A blank `sumRn` means a dry day, not missing data**, and the adapters read it as 0.0 mm. Of 2,128 blank station-days, only four carried any measured `sumRnDur`, and all four were under half an hour of trace precipitation — below the 0.1 mm wet/dry threshold either way. Station outages do not produce blank rows; they produce *absent* rows, which the adapters skip rather than score. There were no absent rows in the sample.
- **A blank `sumRn` and an explicit `0.0` are different states**, and collapsing them is deliberate. `0.0` means precipitation was observed but accumulated below the recording resolution — 411 of 444 such days also carry a positive `sumRnDur` — while blank means none fell at all. Both are dry at a 0.1 mm threshold, so both score as 0.0 mm.

`sumRnDur` (강수계속시간) is published but not read. It would only change a wet/dry call under a threshold below 0.1 mm, which is KMA's own bar; see [`docs/research/aws-network-adoption.md`](./research/aws-network-adoption.md) for why that threshold is fixed.

A day the record cannot yet contain is not a source of absence. ASOS compiles a calendar day's summary hours after midnight, and until it does the service answers the same NODATA as a station with no row, so the 06 KST cohort reads two days back while only the 18 KST cohort reads yesterday, and `performance:observations` refuses an end date newer than that same two-day boundary.

`lib/cache.ts` provides process-local TTL caching with single-flight refreshes. If a refresh fails and an expired value exists, the provider serves that value with `stale: true`. This is an availability fallback, not durable storage; serverless instances do not share it.

No forecast provider failing is a route failure. `/api/local-forecast` answers 503 `forecast_unavailable` only on an unexpected server fault; when every source is down it answers normally with null numbers, because a page that says it does not know is honest and an invented number is not.

Nationwide recent performance uses PostgreSQL as its store. `performance_stations` contains official observation-station metadata; `performance_captures` contains one immutable next-day provider capture per station/date/cohort; `performance_observations` contains one correctable official station-day result; and `performance_seed_comparisons` contains retrospective archive evidence, kept in its own table so it can never be read as a Forecast Capture. These tables never store a user query, browser identifier, or user coordinate. The 06 and 18 KST scheduled cohorts are kept separate, and retries preserve the first capture for a station/date/cohort.

Each forecast provider exposes one Provider Snapshot read. Its availability, cache/freshness metadata, and normalized current, hourly, and daily weather come from the same cached generation. The shared provider instance and its ID-keyed cache are reused by `/api/local-forecast` and by the scheduled nationwide capture. A missing configuration or failed fetch yields an empty non-OK snapshot; stale last-good data stays an available snapshot with `stale: true`.

## Fusion rules

- `/api/local-forecast` requests every forecast provider at the validated Forecast Location and targets the next KST calendar day.
- Forecast-provider order is Open-Meteo, KMA, Pirate Weather, WeatherAPI, then Visual Crossing. The first available current snapshot in that order is the comparison primary, and the first with an hourly series supplies the ribbon. A new source is appended for that reason: inserting one earlier moves which provider's hourly series the ribbon draws.
- The 24-hour ribbon — eight 3-hour blocks — is **not** blended. It comes from one provider, and the page names that provider alongside it. Hourly series differ between providers in issue time, resolution and what counts as precipitation, so averaging them would produce a curve none of them issued. The headline probability beside it remains the multi-provider blend.
- The ribbon's mm lane and the verdict sentence's window total come from the **same** provider's hourly precipitation amounts (`precipitationAmount` on the hourly series — Open-Meteo requests the hourly `precipitation` field; providers that publish no hourly amount simply produce no lane). The lane is drawn on its own mm scale, never the probability axis, and the blended daily amounts on the day cards remain a separate, separately-counted claim.
- The Recent Performance Profile comes from the ASOS Station Match that passes the configured distance and elevation gates. The API returns the station name and distance rather than presenting station evidence as exact-coordinate truth.
- Probability performance uses all completed wet and dry days in a 60-day lookback with a 14-day half-life. Rainy-day amount MAE is separate.
- Learned influence requires comparable sample, wet-day, and dry-day evidence; then it ramps and remains bounded by provider floors and caps. A provider that has not yet met that bar sits at its equal share rather than at the floor, so a source that accumulates evidence slowly is not demoted for it.
- Operating defaults are a 100 km station-distance gate, 400 m elevation-difference gate, 0.1 mm rain threshold, 50% decision threshold, 30-to-60-capture influence ramp, 5–60% provider bounds, and an `exp(-12 × Brier)` score transform. A provider becomes eligible only with at least one wet and one dry day in its sample, and the profile needs two eligible providers before it leaves Equal Fallback. The transform is monotonic, so it can never reorder providers; sharpness was raised from 4 because at 4 a real threefold difference in wet-day miss rate compressed to a 1.18× weight spread, which read as "every service is the same". These are defaults to validate, not coverage or accuracy guarantees.
- The Prospective Benchmark freezes adaptive and equal outputs at capture time and later scores them on identical completed rows. Regression or insufficient benchmark evidence suspends learned influence.
- Missing current providers are omitted and the remaining current weights renormalize. Missing performance evidence selects equal influence; it never becomes a numeric zero score.
- Recent Performance Profile influence applies only to the measured next-day horizon. The later outlook days stay on Equal Fallback until separately captured prospective evidence exists for those lead times.
- Scheduled forecast capture projects daily data only from available snapshots. A non-OK provider or a missing target date is omitted, never represented as a made-up forecast.
- **Not every provider publishes a daily precipitation amount, so the amount blends fewer sources than the probability.** Open-Meteo, WeatherAPI and Visual Crossing publish one directly. Pirate Weather publishes `precipIntensity`, the unconditional 24-hour mean in mm/h, and `precipIntensity × 24` equals the sum of its own hourly series exactly — that is its published total, not a derived estimate. KMA publishes only `PCP`, which is categorical: exact values like `3.0mm` appear alongside buckets like `1mm 미만`, `30.0~50.0mm` and `50.0mm 이상`, and the buckets appear precisely on heavy-rain days. Summing those would require inventing a value inside a range, so KMA's amount stays `null`. Do not "fix" it with a bucket midpoint.
- MET Norway is not requested at all. Its Locationforecast product publishes `precipitation_amount` for Korea but no `probability_of_precipitation` — that field is Nordic-only in their detailed model — and both the served blend (`lib/localForecast.ts`) and the capture (`lib/performance/capture.ts`) require a next-day probability, so every forecast it returned was discarded. The provider was removed once the scheduled pipeline that scored it on its own terms was retired. `PrecipProviderId` still admits `met-norway` because stored capture and seed rows carry it historically; `PERFORMANCE_PROVIDERS` filters it out at read time so a service that cannot influence the blend is never scored beside it.

## Attribution

The UI must retain the applicable credits: Kakao Map for administrative search; Open-Meteo; 기상청 (KMA); Pirate Weather; WeatherAPI; and Visual Crossing. That list is exactly what the served page displays, and it must stay that way — crediting a source the reader is not being shown is as much a false claim as comparing one the forecast never reads. MET Norway is absent for that reason, and so are CARTO/OpenStreetMap and RainViewer: the basemap and the rain-approach signal went out of the product together with the radar, so nothing derived from either reaches a visitor any more. The service-area geometry is derived from 국가데이터처 SGIS 행정구역 경계, published with no stated usage restriction; it is used server-side only and no boundary geometry is displayed. `/behind-the-data` additionally names SGIS in its sources footer — that page exists to describe how the system decides, so naming a source it depends on is provenance rather than a credit for displayed data, and the credit rule above is unchanged. Check provider terms before changing commercial use, caching, or redistribution behavior.

Kakao is credited in **plain text only, and deliberately so**. Kakao Developers site terms 11-10 prohibit using Kakao trademarks or logos without explicit consent, and Kakao states that Local API search results require no source attribution or branding at all — the logo guidance applies to the Kakao Map SDK, which this project does not use. Adding a Kakao logo would move the project from compliant to non-compliant.

Kakao Local search is **live call only**. Site terms 11-3 bar replicating API results without prior approval, and Kakao's Maps team treats a cache kept to reduce request frequency as a temporary database that their operating policy forbids, explicitly including a one-hour cache. `/api/locations/search` therefore answers `no-store` and nothing about a Kakao response is persisted. The daily quota is 100,000 requests per app, far above this project's traffic, so there is no pressure to revisit that. Serving Local results alongside a non-Kakao basemap is permitted; Kakao does not restrict use with third-party APIs.
