## Findings

### 5. HIGH: The social image presents an invented forecast number

Rules: R-17, R-38, C-5.
Reason: the deployed preview prominently displays a fixed 35% beside LIVE SOURCES without a location, date, source measurement, or example label.

Evidence: `app/opengraph-image.tsx:34` hardcodes `35`. The production image visibly matches it. There is no forecast read in the image renderer.

Proposed fix: remove the percentage and let the product name and rain-forecast description carry the image. If a sample is deliberately retained, label it visibly as an example. Do not replace it with another invented number.

### 6. HIGH: The benchmark copy calls a tie a win

Rules: R-36, C-5.
Reason: the implementation accepts an equal score, while several descriptions promise that learning must win.

Evidence: `lib/performance/performance.ts:314` passes when `adaptive <= equal + 1e-12`. `lib/behindTheData.ts` maps every passing verdict to `이김` and describes learned mode as beating the average. `app/behind-the-data/page.tsx:107` says weights are used only when they win; its later heading says `이기지 못하면 끕니다`. The same page correctly states `단순 평균 이하의 Brier` in the detailed rule, contradicting its headline. About says learning stops “the day that stops helping”; the release says it suspends when it stops beating equal weighting.

Proposed fix: describe the actual threshold as “단순 평균보다 나쁘지 않고, 필요한 표본이 모였을 때”. Label the verdict `기준 통과`, or separately distinguish ties if the underlying unrounded comparison supports that distinction. State that the decision updates when evidence is read, without promising an instantaneous daily switch. Preserve the scoring policy.

### 7. HIGH: Several conditional state messages describe the wrong state

Rules: R-17, R-27, R-36.
Reason: fixed prose turns variable evidence states into claims of exactly half strength, no history, or permanent fallback.

Evidence:

- `lib/behindTheData.ts:129` labels every ramping state `아직 절반의 세기`, although `rampProgress` varies from 0 to 1 across the sample range (`lib/performance/performance.ts:356`).
- Its equal-fallback detail says no scored records exist. The mode also covers records that exist but fail evidence requirements.
- `components/local/LocalForecastExperience.tsx:1345` and `:1405` say there are no performance records whenever weighting is off, including benchmark suspension with existing records.
- `app/behind-the-data/page.tsx:343` says new regions remain equally weighted `영원히`. Scheduled collection is specifically intended to let them graduate.
- The seed explanation says influence moves toward equal weighting by half, without clearly naming the starting weights; it also describes every suspension as regression, though insufficient comparable samples can suspend learning too.

Proposed wording: `학습 가중치를 점진적으로 반영 중`, `가중치를 적용할 근거가 충분하지 않아 같은 비중으로 계산했습니다`, and `최근 비교 기록이 충분히 쌓이기 전까지 과거 자료를 일부 반영합니다`. Use the actual reason for a suspension. Explain seed influence as halfway between equal weights and the weights calculated from archive evidence.

### 8. HIGH: The seed table's summary count belongs to a different dataset

Rules: R-17, R-38, C-5.
Reason: the surrounding labels make a live sample count look like the size of the historical sample below it.

Evidence: the public Seoul forecast displayed `과거 예보 기록` and `비교한 예보 14일`, followed by provider rows containing `비 온 26일`. `lib/localForecastView.ts:313` derives `comparisonSampleCount` from live score rows even in seed mode. `components/local/LocalForecastExperience.tsx:706` renders it as days in the seed section. Each seed row already has its own `sampleCount`.

Proposed fix: label live and archive sample counts separately, or derive the archive summary from the archive rows and show each provider's denominator. Label the adjacent benchmark as a separate prospective comparison, with its sample count and whether a verdict is available. Preserve the two evidence classes and their values.

### 9. HIGH: Introductory claims omit the conditions on weighting and fallback

Rules: R-36, C-5.
Reason: short descriptions promise recent observed accuracy weighting as the general behavior, although the live example currently uses retrospective model evidence and other states use equal weights.

Evidence:

- About: `Weights five providers by observed local accuracy`.
- `app/layout.tsx:24`: `가까운 관측소의 최근 관측 성능을 반영합니다`. “관측 성능” also makes the observation sound like the thing being scored.
- The chooser says influence is adjusted according to recent observed results without naming tomorrow or the evidence requirement.
- README line 41 promises equal influence until every evidence gate passes, while lines 74–84 describe a seeded exception.
- The release's `Everything degrades to a usable forecast` and its claim that any unavailable provider causes equal influence exceed the implementation. The application has an actual forecast-failure state; one provider failing does not necessarily disable learned influence among responders.

Proposed About text: `오늘비: South Korea rain forecasts from five weather services. Tomorrow's blend can use nearby-station evidence, with equal weights when the evidence does not support an adjustment.`

Proposed site introduction: `오늘·내일 비 예보를 여러 날씨 서비스와 비교합니다. 내일 예보는 가까운 관측소의 비교 기록이 충분할 때 서비스별 비중을 조정합니다.` Explain archive-based provisional weighting beside its active state. In README and the release, distinguish provider failure, evidence failure, and a forecast that cannot be loaded. Keep the release's historical provider count unless correcting an independently established historical error.

### 10. HIGH: The record page overstates data freshness

Rule: R-36.
Reason: a cached read is described as fresh database evidence on every visit.

Evidence: production displays `지금 이 순간의 증거: 페이지를 열 때 데이터베이스에서 읽습니다` (`app/behind-the-data/page.tsx:144`). `lib/localForecast.ts:195` sets the record evidence TTL to ten minutes, and station/profile reads use it. README line 32 similarly describes rendering from the database on every request, while line 144 explains the sharing accurately.

Proposed wording: `최근에 읽은 채점 기록: 최대 10분 동안 같은 기록을 보여줍니다.` Retain the actual `읽은 시각`. Rewrite the README caption to distinguish rendering the page from refreshing its evidence.

### 11. HIGH: The forecast footer broadens the privacy promise

Rule: R-36, C-5.
Reason: “not stored on the server” is broader than the documented database boundary and contradicts the chooser's cache disclosure.

Evidence: `components/local/LocalForecastExperience.tsx:1443` displays `사용자 위치는 서버에 저장하지 않음`. The chooser at lines 595–600 explains transmission to the server/providers and temporary coordinate-based server-memory caching. README line 38 correctly limits the promise to the performance database.

Proposed wording: `사용자 좌표는 성능 기록 DB에 저장하지 않습니다.` Keep the existing transmission, device-storage, and temporary-cache disclosures available. This finding concerns consistency of the product's own statements, not a certification of infrastructure logging or third-party retention.

### 12. HIGH: The rain sentence overstates what the threshold establishes

Rules: R-36, R-38.
Reason: not reaching a 40% threshold is described as no rain news for 24 hours, including a branch with missing probabilities.

Evidence: `readTimeline` defines a wet block by `precipMax >= threshold`; nulls are not wet. `RainSentence` at `components/local/LocalForecastExperience.tsx:879` says `앞으로 24시간, 비 소식은 없습니다` whenever there is no run. Thus all values below 40%, or all values missing in a nonempty timeline, reach that sentence. The page also says `40% 넘는` although the comparison includes exactly 40%. Accessible block text says `여기서 비가 시작됩니다`, presenting the threshold crossing as an event.

Proposed fix: use `40% 이상` consistently. Distinguish “발표된 시간대에는 강수확률 40% 이상인 구간이 없습니다” from an unavailable timeline. Describe a wet run as `비가 예상되는 시간대` and preserve the single-provider attribution. This is a wording/state-branch correction, not a proposed threshold change.

### 13. HIGH: Two explanations turn limited evidence into absolute conclusions

Rules: R-17, R-36, C-5.
Reason: sampled geographic coverage and shared capture times do not establish the universal statements the prose makes.

Evidence:

- The live limits section says no inhabited place is more than 30km from an ASOS station (`app/behind-the-data/page.tsx:385`); README line 246 says no populated place is more than about 30km. The cited research's relevant comparison used 36 administrative centres and reports a maximum of 30.2km (`docs/research/nationwide-verification-coverage.md:109`). That is useful evidence about those points, not a census of every inhabited location.
- The live lead-time explanation says timing drift is noise and cannot favor a provider (`app/behind-the-data/page.tsx:277`); README line 54 makes the same claim. Providers sharing a retrieval time alone does not prove their relative skill is unaffected by forecast horizon or update timing.
- The same live paragraph still says `네 서비스`, while the current registry and attribution list contain five compared providers.

Proposed fix: identify the geographic sample and measured maximum, or omit the universal sentence. Describe shared capture timing as a mitigation and leave the effect of delayed collection as a limitation. Use `같은 수집에 포함된 서비스` for the timing explanation. Do not manufacture a population-wide result or causal validation.

### 14. HIGH: Prohibited punctuation remains across README and GitHub descriptions

Rule: R-02.
Reason: the selected filter prohibits U+2014, which the earlier UI-only correction did not cover on these surfaces.

Evidence: README contains 36 occurrences. The About description and release title/body contain it. 98 of the 108 owner-authored issue/PR records contain it in their title or body; the exact records and occurrence counts are in the inventory. The existing rendered-copy AST check covers app strings, not README or GitHub.

Proposed fix: replace authored prose separators with sentence breaks, commas, colons or parentheses according to meaning. Keep original code/log excerpts and quoted third-party source text faithful; inspect matches before editing. Preserve historical facts, commands, URLs, test counts, and issue relationships. Punctuation alone is not evidence of AI authorship.

### 16. LOW: README captions and the opening bury the product in design rationale

Rules: R-05, C-3.
Reason: multiple italic paragraphs explain the author's choices at essay length before readers reach the product contract or setup.

Evidence: README lines 8, 16, 20, 24, 28 and 32. The opening combines the rain window, timeline, day cards, prospective evidence, a profile and a station match in one sentence. Captions repeatedly use defensive contrasts and product personification. Line 102 explains why a reader supposedly does not understand a sentence instead of simply describing the record link. Line 104 recounts the absence of a retired scene. The rest of the README already has dedicated architecture and evidence sections.

Proposed opening: `오늘비 shows rain forecasts for a chosen location in South Korea. Compare the next 24 hours, today's forecast, and tomorrow's forecast from five weather services. Tomorrow's blend can use nearby-station evidence when the relevant checks pass.`

Proposed forecast caption: `The timeline shows eight three-hour blocks from one named provider, with rain probability above and rainfall amount below. The heading summarizes the expected rain window.`

Apply the same edit to all five captions: one or two sentences describing the visible screen. Keep substantive scoring conditions in the scoring section, implementation boundaries in Architecture, and historical design reasoning in the linked ADRs. Correct the caption's old missing-value “dash” description to match the current explicit labels. Preserve setup commands, licensing, and useful limitations.

### 17. HIGH: Some GitHub descriptions use slogans and unqualified guarantees

Rule: R-36; copywriting patterns: aphorisms, significance inflation, negative parallelism.
Reason: rhetorical conclusions inflate otherwise concrete technical changes, and some go beyond what their evidence establishes.

Examples:

- [PR 132](https://github.com/mhju0/raintoday/pull/132): `A count drifts silently; a set cannot.` The actual improvement is a test comparing declared and used variables; it does not establish an impossible-to-drift set.
- [PR 128](https://github.com/mhju0/raintoday/pull/128): `ten minutes cannot hide a change of verdict`. A cache can briefly retain a verdict across an update. Preserve the measured timings as dated measurements, but qualify the cache claim.
- [Issue 112](https://github.com/mhju0/raintoday/issues/112): `honesty machinery` introduces a page about scoring records with a promotional abstraction.
- The release says a page showing only wins `would not be worth publishing`, and labels missing data `Honest absence`. These appraisals add little beside the actual inclusion and missing-value rules.

Proposed fix: lead each affected description with its concrete problem, resulting behavior, and relevant validation. For PR 132: `Tests now compare the environment variables declared in .env.example with those used by the application. They detect unused declarations and missing entries.` Remove recurring moral or theatrical conclusions while retaining real investigations, self-corrections, unresolved decisions and dated measurements.

This finding approves editorial cleanup of authored descriptions with these patterns, not rewriting every historical issue as if it describes today's application. The latest PRs 134 and 136–138 already lead with concrete changes and evidence. Dependabot's quoted upstream release notes should remain quotes. Read each proposed historical change as a historical document before publishing it.
